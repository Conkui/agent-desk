# HAPI 界面复盘与重设计依据

日期：2026-10-22。本文保留第一版复盘与设计依据；第二版的实现范围、交互预览和验证见 [design-v2.md](design-v2.md)。

## 本轮检查范围

重新检查上一版桌面与手机截图、WorkspaceOverview、WorkspaceBrand 和样式文件；阅读 Linear 的界面改版案例，查看其官方侧栏前后对比图，阅读 Apple 手机导航准则及 GOV.UK 状态列表的使用研究。

这些资料支持下面的设计判断，但没有替代真实用户测试。尺寸和布局是下一轮原型的起点，不能视为已验证结论。

## 上一版具体失败在哪里

| 问题 | 页面证据 | 使用影响 | 后续处理 |
|---|---|---|---|
| 首屏围绕欢迎语组织 | 1440×1000 截图中，最近会话约从 y=470 开始 | 每次打开都要越过重复内容才能找到工作 | 顶部只保留当前位置、搜索和新建入口 |
| 状态数量没有操作路径 | 三个大数字只显示数量 | 用户看到需要处理，却仍需自己定位会话 | 将“需要处理”做成可进入的具体请求列表 |
| 两处列出同一批会话 | 左栏和右侧最近会话重复 | 占用空间，无法形成列表与内容的关系 | 导航、列表、当前会话各自承担一种职责 |
| 导航宽，文字仍被挤压 | 默认左栏 420px；待处理状态、数量和时间争抢同一行 | 任务标题先被截断，关键内容反而看不清 | 降低导航宽度；列表行分配固定状态区与可伸缩标题区 |
| 控件语义不清楚 | 图标行缺文字；同一局部出现多个加号 | 新用户需要猜测功能与操作范围 | 主要操作使用文字；目录内新建只在目录上下文出现 |
| 内部导航使用外链箭头 | 打开会话、设备管理也标 ↗ | 视觉信号与实际行为不一致 | 内部跳转沿用列表选中或展开行为，外链才使用外链标记 |
| 技术说明常驻工作区 | Tailscale 文案占据底部区域 | 日常使用反复看到低频安装说明 | 放入设备连接向导；故障时提供对应修复入口 |
| 手机布局只保留一列 | 小图标在顶部，条目过紧，下面大面积空白 | 不能快速判断需要处理什么，也缺稳定导航 | 单独设计手机的列表、审批与继续对话流程 |
| 空状态缺少条件判断 | 无 Runner 时仍以新建会话为主入口 | 用户进入表单后才发现没有可用设备 | 分清未连接设备、未安装 CLI、尚无会话三种起点 |
| 验证目标过低 | 已有记录只验证构建、无溢出和跳转 | 无法证明界面好用、美观或操作可理解 | 加入任务完成路径、信息识别与内容压力检查 |

## 从参考资料提取的规则

### 1. 稳定的导航与内容层级

Linear 的 2026 年改版将导航与工作内容的视觉权重区分开，减少过量图标和分隔线，统一动作的位置。其侧栏前后对比图中，非当前项降低存在感，间距更均匀。

应用到本项目：当前位置、搜索、新建、会话操作各有稳定位置。彩色背景、粗体和边框必须表达当前选中、需要注意或区域归属。不能用它们把每个区域都强调一遍。

来源：[Linear — A calmer interface for a product in motion](https://linear.app/now/behind-the-latest-design-refresh)

### 2. 保留工作内容的空间

Linear 的 2024 年案例把对齐、信息密度、不同环境与多种视图的压力检查纳入设计，而非只制作一张理想状态的截图。

应用到本项目：首先设计“列表 → 当前 Agent 输出”的连续阅读。任务图、文件变化与权限设置按需打开；只有一个 Agent 时也应自然成立。宽屏可保留辅助栏，窄桌面默认收起。不能照搬多栏结构而不检查正文宽度。

来源：[Linear — How we redesigned the Linear UI](https://linear.app/now/how-we-redesigned-the-linear-ui)

### 3. 手机端需要自己的导航

Apple 的 Tab bars 指南强调：标签栏用于顶层目的地，导航保持稳定；图标配合清楚的文字标签，重要徽标避免泛滥。

应用到本项目：手机可从“任务、待处理、设备”三个目的地开始探索；设置放在设备或个人配置入口。新建属于当前页动作。进入任务后仍能明确返回来源，并保留原有位置。

这是本项目的设计建议，并非 Apple 对此产品信息架构的规定。

来源：[Apple HIG — Tab bars](https://developer.apple.com/design/human-interface-guidelines/tab-bars)

### 4. 状态服务于下一步动作

GOV.UK 的状态列表研究指出，用户会将过于突出的状态误当作按钮；完成项降低强调，有助于发现待办项。

应用到本项目：颜色配合文字；审批显示具体动作，例如“请求运行 npm test”，而非只显示“待处理 1”。整行能进入详情，真正的批准/拒绝按钮有清楚边界。涉及权限时在详情展示命令、目录、作用范围与有效期。

GOV.UK 的任务列表有自己的适用条件，不把这种列表直接当作 Agent 依赖图或调度模型。

来源：[GOV.UK Design System — Task list](https://design-system.service.gov.uk/components/task-list/)

## 下一轮原型围绕四条真实路径

### 初次使用

检测本机工具 → 展示可用/缺失及原因 → 选择工具 → 选择目录 → 开始首个任务。

已安装、已配置、可执行、登录有效分别展示证据。模型和权限提供可理解的默认项，高级参数在需要时展开。只有一种 CLI 时可直接选择它兼任协调与执行。

### 日常工作

进入上次项目 → 扫描任务标题与最近进展 → 打开某个 Agent → 阅读输出 → 补充一句要求。

项目是工作范围，任务是目标，Agent 会话是执行与对话载体。三者需要关联，不能仅把“会话”换成“任务”的标签。工作流 API 实现前，真实页面继续准确显示会话。

### 手机审批

通知或待处理入口 → 请求发生在哪个任务 → 看清操作内容 → 决定允许或拒绝 → 看到服务端确认的处理结果。

审批期间避免日志滚动把操作区带走；允许前可查看完整命令。离线、请求过期、Agent 已取消时提示真实结果。提交中的按钮防止重复点击，不能在服务端确认前显示成功。

### 离线恢复

显示“电脑离线”和最后更新时间 → 保留已缓存内容 → 提供明确重试 → 重连后补齐事件与审批状态。

客户端断网与 PC 离线分开表达。不让“正在运行”在数据过期后继续看起来实时有效。

## 视觉与内容的起点

- 默认使用系统无衬线字体；代码与原始输出使用等宽字体。实际检查 Windows、Android 的字体回退和中英文混排。
- 正文从 14px 左右开始试排，次要信息避免大量小于 12px；界面标题约 18–20px，不占用首屏作为大幅宣传语。
- 桌面列表通过对齐和分组表达结构；长标题优先保留辨识内容。手机允许合理换行，状态与时间不挤压标题。
- 以 4/8px 的间距步进对齐；组件圆角根据容器层级收敛，避免逐层套圆角卡片。
- 一种交互强调色，状态色按含义使用。完成项和设备健康信息不与正在等待的审批抢注意力。
- 图标使用统一库与尺寸。加号、箭头和字母头像仅在含义明确时出现。
- 手机主要操作触控区从 44×44 CSS px 开始检查；键盘打开后，输入和发送入口仍可用。这是原型目标，非设备实测结果。
- 首屏存在一个清楚的主要操作；同一范围不反复提供相同的新建按钮。
- 文字描述实际对象与行为：“连接电脑”“新建任务”“查看输出”“允许本次”。帮助文案只在相应问题出现时提供。

## 原型验收方法

| 情况 | 应能直接判断或完成 |
|---|---|
| 首次打开，没有 Runner | 知道需要先连接设备，并能进入连接步骤 |
| 只有 Codex | 能创建任务并理解它兼任协调与执行 |
| 3 个 Agent 同时工作 | 找到各自任务、最近进展和当前输出 |
| 一个待审批请求 | 从列表或通知进入，读清命令并看到处理结果 |
| 30 条会话、长中文标题与 Windows 路径 | 搜索和浏览有效，标题不会被状态挤得无法辨认 |
| 390px 手机，键盘打开 | 返回、输入、发送和审批都可操作 |
| 无会话、请求失败、断线和重连 | 不产生相互矛盾的状态或无效主按钮 |
| 日常再次打开 | 直接回到工作内容，不重复阅读安装或宣传文案 |

下一步产物应是可以逐步操作的桌面任务详情与手机审批原型，覆盖上述状态。需要同时评估辨识、操作和视觉质量；构建通过和截图没有溢出只证明技术层面的部分正确性。
